# Architectural Decisions

Format: decision — rationale — alternatives rejected. Unresolved business questions at the end.

> **Source of truth (D32):** `BPO_ASSET_MANAGEMENT_TAS_v2.0.md` is the authoritative specification for all new development. `BPO_ASSET_MANAGEMENT_TAS_v1.0.md` is the historical desktop-prototype specification. `docs/ARCHITECTURE_V2_CLOUD.md` holds the architecture rationale and migration decisions.
>
> **Architecture change (2026-10-11, D24):** Decisions D1, D3, D4 (IPC binding only), D5, D7, D11, D12, D13 and D15 apply to the **Electron prototype only**. Domain decisions (D6 migration checksums, D8 hashing and lockout, D9, D10, D14, D16–D23) carry forward unless D24–D32 or TAS v2.0 say otherwise.

## D1. SQLite driver: better-sqlite3 13.0.3 (2026-10-11)
v13 is built on N-API and ships prebuilt `.node` binaries per platform, so the same binary loads in Node 24.14 (tests) and Electron 44 (Node 24.21). No `electron-rebuild` and no C++ toolchain needed (none is installed on the dev machine). Verified in the packaged, fused app (`npm run smoke:packaged`). Synchronous API fits the single-connection main process and gives `db.backup()` (SQLite Online Backup API).
Rejected: `node:sqlite` (loads in Electron 44 with SQLite 3.53.4, but its stability status is lower and better-sqlite3 is the TAS default with a proven API); sqlite3 (async/callback, rebuild needed); sql.js (in-memory, unsafe durability).

## D2. Toolchain versions (2026-10-11)
Electron 44.7.0, electron-vite 4.0.1, Vite 7.3.7, React 19.2.8, TypeScript 5.9.3, Vitest 4.1.11, Zod 4.6.5, Playwright 1.63.0, electron-builder 26.15.3. Pinned exactly. Chose mature lines over packages released days earlier (electron-vite 5.0.0, TypeScript 7.0.2, React 19.3.0, Vite 8). Electron upgrades require re-running the packaged smoke test.

## D3. Renderer served from privileged `app://bundle`, not `file://`
Enables a strict CSP via response headers, a single trusted origin for IPC sender validation, and path-traversal-guarded file serving. Note: Node's `URL.origin` is `"null"` for custom schemes, so origins are compared as `protocol//host` (bug caught by unit test).

## D4. IPC contract
One `ipcMain.handle` channel per command (`bpoam:<group>.<method>`), generated from `COMMAND_NAMES` in `src/shared/api.ts`. Preload exposes a nested `window.api` of functions only — never `ipcRenderer`. Main validates: top-level frame + trusted origin → known command → strict Zod schema (unknown keys rejected) → session/lock state → service-level permission check. Results are `{ok,data}|{ok:false,error:{code,message,correlationId,fieldErrors?}}`; stack traces never cross the boundary. The dispatcher is Electron-independent so it is integration-tested directly.

## D5. Journal mode DELETE (not WAL), synchronous FULL
Single-user, single-connection workload; one-file database simplifies backup/restore consistency. Revisit only with measured need (TAS §4.2).

## D6. Migrations
Ordered TS modules (`src/main/database/migrations`), SHA-256 checksum recorded per version; startup refuses altered history or a newer schema; each migration runs in its own transaction; a verified `pre_migration` backup is taken before migrating an existing database. Applied migrations are never edited.

## D7. Startup never initializes over existing data
A `.initialized` marker is written after first successful init. Missing DB file or an empty schema with the marker present → recovery screen, not a new database. Corrupt files are left untouched.

## D8. Authentication
scrypt (N=2^15, r=8, p=1, 16-byte salt, params stored per hash) via Node crypto — no native dependency. Lockout: 5 consecutive failures → 15 minutes (technical defaults; constants in `src/main/services/auth.ts`). Unknown usernames hash a dummy password (timing parity) and return the same message. Idle lock default 15 minutes (setting). Admin-created/reset passwords force a change at next sign-in. Password minimum 10 characters (technical baseline; can be made a setting if the business requires).

## D9. Authorization
Permission catalog in `src/shared/permissions.ts` is synced to the DB at startup. Super Admin automatically holds every permission and its role cannot be edited. Permissions are re-read from the DB on every IPC call, so role changes/deactivation apply immediately. Invariants: at least one active Super Admin; a user cannot deactivate themselves. UI hiding is convenience only.

## D10. Audit trail
`audit_events` append-only enforced by DB triggers (UPDATE/DELETE abort). Written in the same transaction as the change. Summaries pass through redaction (password/token/hash keys).

## D11. Backup format
`backups/<YYYYMMDDTHHMMSSZ>-<kind>-<hex8>/` containing `database.sqlite` (Online Backup API), `documents/…`, `manifest.json` (format, schema/app version, SHA-256 of every file, row counts, verified flag). Written to `.partial` and renamed only after full integrity + FK check. Restore: validate → mandatory pre-restore safety backup (abort if it fails) → stage → swap DB (+ journal sidecars) and documents → reopen/migrate/FK check → rollback on any failure → audit in restored DB → session ended. Backup IDs are regex-validated; renderer never supplies paths.

## D12. Data locations and environment separation
Production: `%APPDATA%\BPO Asset Management\data\{database,documents,backups,logs}`; dev/test use `BPO Asset Management (development|test)`. `BPOAM_DATA_DIR` overrides (tests/smoke only). Chromium profile data kept in a sibling `chromium` folder. NSIS installer is per-user, keeps app data on uninstall.

## D13. Packaged-binary hardening
Electron fuses: RunAsNode off, NODE_OPTIONS off, CLI inspect off, asar integrity validation + only-load-from-asar on, cookie encryption on. Single-instance lock (one process owns the DB and session). App menu removed and devtools disabled when packaged.

## D14. UI styling (deviation from TAS §3.1 suggestion)
TAS suggests Tailwind + a component library. Version 1 uses a small in-repo component set (`src/renderer/src/components/ui.tsx`) and one token-based stylesheet: zero extra dependencies, CSP-friendly (no runtime style injection), native Segoe UI type (offline, no font bundling). Revisit if the component count grows enough to justify a library; must remain accessible (labels, focus, dialogs).

## D15. Renderer avoids Zod
Plain constants live in `src/shared/constants.ts`; renderer imports schema *types* only. Bundle 232 KB minified. Main always re-validates.

## D16. CSV parser: csv-parse 7.0.3 (M2, 2026-10-11)
MIT, zero dependencies, actively maintained (adaltas/node-csv), CJS + ESM with bundled types, pure JS (no packaging risk; verified in the packaged smoke test). Handles quoted fields, embedded delimiters/newlines and escaped quotes. Its one advisory affects versions below 7.0.2 and only the `columns` option, which we don't use (we parse to arrays). Line endings are normalized to `\n` before parsing, because csv-parse auto-detects the delimiter from the first line and would otherwise merge rows in mixed-ending files. Decoding is strict UTF-8 (`TextDecoder` with `fatal`), with explicit rejection of UTF-16, binary files and xlsx workbooks. Rejected: papaparse (no bundled types, browser-oriented), and a hand-written parser.

## D17. Organization model (M2)
- One `locations` hierarchy (site/building/floor/room/bay/storage/other). Parent rules are structural and kept in `src/shared/organization.ts` (`LOCATION_PARENT_RULES`), and cycles are blocked by the service. **Seats are not a location type**: workstations/seats are a separate `workstations` table (kind `workstation|seat`) placed in a floor/room/bay. This keeps one concept for the future assignment target (TAS §8.2).
- Teams belong to exactly one department; `kind` = `team|process` (BPO client process/LOB).
- `asset_pools` hold only custody metadata (responsible department and/or team, default location). Assets will join pools through assignments in M4, never through a column on pools.
- Nothing is deleted; `is_active` / `employment_status` preserve history. Conservative integrity defaults: a department, team or location can't be deactivated while active children, current employees, active workstations or active pools reference it. Reactivating a child requires an active parent.
- Employees: `employee_code` is **user-supplied** (from HR); there is no ID generation. It is unique case-insensitively (trim + upper-case). Exited status is set only via deactivation, with a mandatory exit date and reason. Deactivation keeps department/team/manager links and never touches assets. Exited staff can't be chosen as a new manager or lead. Edits to an exited record require reactivation. A team without a department implies the team's department.
- Personal fields (name, email, phone, notes) are audited as "changed" without their values.

## D18. Employee import policy (M2)
- Flow: native picker (main process reads the file; renderer never sends paths) → in-memory session (owner-bound, 30-minute TTL, max 5) → mapping + preview (read-only) → commit.
- Commit re-validates against the current DB **inside the write transaction**. Any write or constraint failure rolls back every row.
- Default: any rejected or duplicate row blocks the import. The user may explicitly tick "skip rejected and duplicate rows". Accepted rows then commit atomically, and the skip choice is recorded in the audit summary.
- Duplicates: an Employee ID already in the DB, or repeated in the file, is a *duplicate* (never overwrites, never picks a winner). Duplicate email is **configurable** (`employeeDuplicateEmailPolicy`: `warn` default | `reject`).
- Import creates only; updating existing employees via import is out of scope.
- Correction model: fix the source file and choose it again, or remap columns/date format in the preview. There is no in-app cell editing.
- References must already exist (department/team/location by code or name, unambiguous). Managers may be existing current employees or other rows in the same file. Loops and rows whose manager row fails are rejected.
- Dates use the format chosen per import (YYYY-MM-DD / DD-MM-YYYY / MM-DD-YYYY), never guessed. Exited employees are not importable (the exit flow needs a date and reason).
- Cells starting with `=` or `@` get a warning and are stored as plain text, never evaluated.
- Limits: 5 MB, 10,000 rows. Audit summary: counts, file name, SHA-256, size, mapped field names, options. No row data.

**Decision:** when .xlsx import is approved, use **read-excel-file** (exact pin). Either bundle it into the main build (exclude it from `externalizeDepsPlugin`) or rely on Electron 44 / Node 24 `require(esm)`, and verify in the packaged smoke test. Add an adapter that produces the same `{headers, rows}` structure as `parseCsv`, so the existing validation/commit pipeline is reused unchanged. Required hardening: size limit before reading, decompressed-size/cell-count limits (zip bomb), first sheet only (or an explicit sheet choice), read cached values only (never formulas), and dates converted from Excel serials with the 1900/1904 date system handled. Mitigate the single-maintainer risk by pinning exactly and reviewing the changelog on upgrade. Status: **next planned import enhancement** (not in the approved M2 scope; no dependency added).

## D20. Asset codes (M3, business decision 2026-10-11)
Default `AST-000001`. Format = prefix + separator (`-`, `/` or none) + zero-padded sequence (3–10 digits; numbers grow past the padding, never truncated). Stored in a single-row `asset_code_config`. Only `assets.configure_codes` (Super Admin by default) may change it, with a mandatory reason, and the change is audited. `next_number` can only increase, and a value whose code already exists is refused. Codes are issued inside the asset-insert transaction (counter read → skip existing → increment), so a failed insert doesn't consume a number. Uniqueness is enforced by `UNIQUE(asset_code)`. A trigger makes `asset_code` immutable. The immutable UUID primary key is separate. Codes carry no category, department, location or employee information.

## D21. Asset model (M3)
- Separate dimensions (TAS §7.1): `lifecycle_status` (active/retired/disposed/lost), `operational_status` (ready/under_maintenance/non_operational/awaiting_inspection) and `condition`. Assignment state is not stored; it will be derived from assignments (M4). DB CHECKs: disposed requires a disposal date; under_maintenance only while active.
- Lifecycle transitions live in `LIFECYCLE_TRANSITIONS` (shared). Retire, lost and found/reinstate need `assets.retire`; disposal or write-off needs `assets.dispose`, a method and a reason. Disposed is final, and disposed assets can't be edited. Reinstated or found assets return as **awaiting inspection**, so they're never counted as ready unchecked.
- `under_maintenance` can't be set by hand; it's reserved for maintenance tickets (M5).
- Categories carry `asset_domain` (IT/facilities), `tracking_mode` and a serial policy (optional / required / required + unique per manufacturer). Uniqueness is DB-enforced via a nullable `serial_unique_key` (`category|manufacturer|serial`) with a UNIQUE index, maintained by the service, including when a category's policy changes. Bulk categories can be defined, but they reject individual asset registration; stock arrives with procurement (M6).
- Models are catalogue entries. Assets **snapshot** manufacturer/model at registration, so catalogue edits never rewrite history.
- Money is integer minor units in the organization's base currency (`parseMoneyToMinor`; no floats). Cost and disposal proceeds are visible and editable only with `finance.view_cost`. Users without it can't set or clear them, and audit summaries record only `costRecorded`/`costChanged`, never amounts. Depreciation columns are deliberately not created yet (TAS §12).
- Physical location references the existing `locations` hierarchy (M2); filters include sub-locations via a recursive CTE.

## D22. Documents (M3)
`documents` (generated storage key `assets/YYYY/MM/<uuid>.<ext>`, original name, MIME, size, SHA-256) + `document_links` (polymorphic owner validated by the service; soft-removed with who and when; files are never deleted). Allow-list: pdf, png, jpg/jpeg, webp, txt, csv, docx, xlsx; 20 MB max; magic-byte check against the extension. Files are picked via the native dialog in main. "Open" uses the system viewer only for pdf/images/txt, after re-verifying the checksum; other types are "Save copy" only. Missing or tampered files are flagged or refused. Documents are part of every backup and restore (existing D11 mechanism).

## D23. Labels and scanning (M3)
- **bwip-js 4.11.4** (MIT, zero deps, maintained, bundled types; no advisories, verified 2026-10-11) generates both the QR code and the Code 128 barcode as SVG in the main process (`assets.generateLabels`). It's imported from `bwip-js/node` so TypeScript (bundler resolution) and the CJS main build agree, and only `dist/bwip-js-node.js` is packaged. Rejected: qrcode (no release since 2024, extra deps) plus jsbarcode (needs a DOM/canvas in Node), which would be two libraries instead of one.
- QR payload `BPOAM:ASSET:<uuid>` (opaque, no personal or financial data). The barcode encodes the asset code. The label shows organization name + code + QR + barcode, 64×30 mm, printed with the system print dialog via a print stylesheet. Every generation is audited per asset. Disposed assets get no labels.
- USB scanners are keyboard wedges: a dedicated always-focused field. The configured suffix (Enter/Tab/none; none = 150 ms idle) submits. Lookup is exact only (QR payload → asset code → normalized serial), control characters are stripped, and multiple serial matches are listed. Nothing changes state from a scan. Phone camera scanning remains deferred (TAS §10.4 security spike); no local HTTP server was added.
- Asset CSV export: native save dialog; every cell quoted; `= + - @ TAB CR` prefixed with `'`; UTF-8 BOM; needs `assets.view` + `reports.export`; cost columns only with `finance.view_cost`; audited with filters and row count.

## D24. Architecture change to a cloud multi-user web application (2026-10-11)
The requirement changed: multiple departments must share current records from different computers. Version 1 becomes React SPA + central API + PostgreSQL + object storage, with server-side auth and RBAC. The Electron/SQLite code stays in `src/` as a frozen prototype and migration reference; partial standalone M4 work is preserved on branch `wip/m4-standalone-sqlite` (`2b9556f`). Full rationale, migration matrix and plan: `docs/ARCHITECTURE_V2_CLOUD.md`.

## D25. Backend: Fastify 5 + node-postgres + checksummed SQL migrations + Zod (no ORM)
Compared with NestJS + Prisma (ARCHITECTURE_V2 §3). Fastify + `pg` keeps the prototype's service style (plain async functions, explicit SQL), so domain logic ports with minimal change. It reuses the dispatcher and command contract, supports every PostgreSQL feature already relied on (partial unique indexes, row locks, triggers, CHECKs, recursive CTEs) and has a small dependency surface. Prisma can't model partial indexes, triggers or CHECKs and its next major was pre-release; NestJS would force a structural rewrite. Exact versions are pinned when installed.

## D26. Offline policy: online-only business transactions (provisional, conflicts with TAS)
The TAS required offline operation; a cloud system can't guarantee non-conflicting assignments offline without a sync design. V1: every state-changing business transaction requires a live API connection. Cached read-only views or drafts may come later, clearly labelled. No offline sync is built. **Open business decision U1.**

## D27. API transport: typed RPC over HTTPS reusing `CommandMap`
`POST /api/rpc/<command>` with JSON in the same `Result` envelope. Binary data uses dedicated upload and download routes. This keeps one typed contract for server, web client and tests. State-changing calls require the `X-BPOAM-Request` header and a matching `Origin` (CSRF), plus SameSite cookies.

## D28. Sessions: server-side, PostgreSQL-backed, hashed IDs
256-bit random ID in an `__Host-` cookie (HttpOnly, Secure, SameSite=Lax); only the SHA-256 is stored. Idle timeout (setting) + absolute lifetime (12 h). Revoked on logout, password change or reset, deactivation and role or permission change. Per-IP and per-username login rate limits on top of the per-account lockout (D8). Rejected: JWT in localStorage (not revocable, XSS-exposed).

## D29. Document storage abstraction
`DocumentStorage { put, get, exists, delete? }` with a `LocalStorage` driver (development and tests) and an `S3Storage` driver (production, any S3-compatible service; MinIO in compose). Upload validation from D22 is unchanged. Files are served only through the authorized download route, never via public URLs.

## D30. Deployment: one stateless container + managed PostgreSQL + object storage
Node 24 LTS image serving API + SPA behind a TLS load balancer; 1–2 instances. Managed PostgreSQL backups with PITR replace the in-app backup feature. `docker compose` (PostgreSQL + MinIO) for local and staging. No Kubernetes, microservices, brokers or Redis at this scale. Provider and region are open (U4).

## D31. PostgreSQL test strategy
Integration tests run against a **real** PostgreSQL. The harness uses `TEST_DATABASE_URL` if set; otherwise it starts an ephemeral cluster (`initdb` + `pg_ctl` on a free port in a temp directory) once per test run and creates a fresh database per test file. Docker is an alternative for CI. SQLite-specific prototype tests remain for the prototype.

## D32. TAS v2.0 adopted as the authoritative specification; roadmap aligned (2026-10-11)
- **Document hierarchy:** TAS v2.0 (spec) > accepted decisions in this file > `docs/ARCHITECTURE_V2_CLOUD.md` (rationale) > TAS v1.0 (historical). TAS v1.0 keeps its content plus a historical-status notice.
- **Roadmap:** follow TAS v2.0 §22: W0 architecture, W1 server foundation, W2 business modules on PostgreSQL/API (organization, employees, import, catalogue, assets, documents/storage, labels, scanning, exports), W3 browser integration, W4 allocation and exit clearance, W5 maintenance and physical audit, W6 procurement/receiving/approvals, W7 finance, reporting and hardening, W8 deployment, recovery drills, data migration and pilot. This **replaces** the first-draft numbering in which W5 was the SQLite→PostgreSQL tool and W6 deployment. Both now sit in W8 (the migration tool may be built earlier when convenient, but its acceptance is part of W8).
- **Spec gaps against the W1 code, to address in W2 (TAS v2.0 §3.4, §7.1).** These are not silently reconciled:
  1. *API versioning:* W1 serves `/api/rpc/<command>` without a versioning policy. W2 must either adopt a versioned prefix or document a policy. This is a technical choice to make at W2 start; the current code is unchanged.
  2. *Response schemas:* W1 relies on explicit column lists and DTO types. TAS requires response schemas/serialization to prevent field leaks, so W2 must add server-side response shaping (especially for cost and personal fields).
  3. *Route schemas:* D27 validates every command with shared Zod schemas in one RPC route. TAS asks for per-route request/response schemas. Treat the per-command Zod schemas as the route schema for RPC, and add explicit schemas on non-RPC routes (uploads, downloads, exports). Revisit if review requires Fastify-native schemas.
  4. *Idempotency:* retry-sensitive mutations (W4 issue/transfer/return, W6 receipts) need idempotency keys or stable operation IDs. Not yet implemented.
  5. *Document status:* the document metadata must support a scan status (pending/available/rejected/quarantined) so U3 can be honoured; the upload pipeline must not be described as malware-safe while U3 is open.
- **Asset code (TAS B1):** consistent with D20 (default `AST-000001`, configurable, server-generated, immutable, never reused).

## D33. API versioning: `/api/v1` prefix (W2 start, resolves D32 gap 1)
All application endpoints live under `/api/v1/…`: `/api/v1/rpc/<command>`, `/api/v1/uploads/*`, `/api/v1/documents/:id/content`, `/api/v1/exports/*`. Health probes stay unversioned (`/api/health/*`, infrastructure contract). Policy within v1: **additive only**, meaning new commands, new optional input fields and new output fields. A breaking change (removing or renaming fields, changing semantics or types) ships as a new command name (e.g. `assets.searchV2`) or under `/api/v2` with v1 kept for at least one release. W1's unversioned `/api/rpc` had no clients and is replaced outright (no alias kept).

## D34. Per-command request and response schemas on the shared RPC route (resolves D32 gaps 2–3)
Each command is a logical route with its own **input** Zod schema (already present) and a new **output** Zod schema (`server/src/rpc/responses.ts`). Each output schema is type-checked against its shared DTO via `z.ZodType<Dto>`, so the contract and the schema can't drift. The dispatcher pipeline is allow-list → session → input parse (strict objects reject unknown keys) → handler (service-level permission and organization checks) → **output parse**. Output parsing strips undeclared keys, which acts as an allow-list serializer, so restricted internals (hashes, storage keys, other organizations' IDs) can't leak even if a query selects them. An output that fails validation is logged and returned as `INTERNAL_ERROR` (never the raw data). Field-level restrictions that depend on the caller (cost and proceeds without `finance.view_cost`) are enforced in services and covered by tests. Trade-off: one transport route instead of N Fastify routes keeps the shared typed client and avoids a contract rewrite. Fastify-native per-route JSON schemas are used for the **non-RPC** routes (uploads, downloads, exports), where query and multipart validation is route-specific.

## D35. Uploads, downloads, exports and scan status (resolves D32 gap 5; U3 still open)
- **Upload** `POST /api/v1/uploads/documents` (multipart, one file; query `entityType`, `entityId`, `purpose`, all Zod-validated) and `POST /api/v1/uploads/employee-import` (CSV preview). Require session, the CSRF header + Origin, the owner-specific permission (asset → `assets.update`), and that the owner exists **in the caller's organization**. Limits: document 20 MB, CSV 5 MB (enforced while streaming; the proxy limit must be at least this). Extension allow-list + declared MIME + magic-byte signature (prototype D22 rules). The storage key is generated server-side (`<org>/<owner-type>/<yyyy>/<mm>/<uuid>.<ext>`); client filenames are display-only.
- **Download** `GET /api/v1/documents/:documentId/content`: session + view permission on at least one active owner link in the caller's organization; checksum verified before streaming; `Content-Disposition: attachment` by default, `inline` only for pdf/png/jpeg/webp; `X-Content-Type-Options: nosniff`; `Cache-Control: no-store`; audited (`document.downloaded`).
- **Unlink** stays the RPC `documents.removeLink`, a soft unlink with reason (objects are retained; deletion and retention policy remain undefined, TAS §7.2).
- **Export** `GET /api/v1/exports/assets.csv?<filters>`: same filter schema as `assets.search`, `assets.view` + `reports.export`, cost columns only with `finance.view_cost`, formula-injection-safe CSV (D23), audited.
- **Scan status while U3 is open:** `documents.scan_status` ∈ `not_scanned | pending | clean | rejected | quarantined`. With no scanner configured (`DOCUMENT_SCANNING=disabled`, the only supported value now) uploads are stored as `not_scanned`, downloads are allowed, and the API returns `scanStatus` so the UI can show "not scanned for malware". The status is never set to `clean` without a scanner. When a scanner is introduced, new uploads start `pending` and downloads are blocked until `clean`. This is the explicit provisional policy, and **uploads are not claimed to be malware-safe**.
- **Storage:** `DocumentStorage` interface; `LocalStorage` driver (dev/test, key-validated, atomic write). The S3-compatible driver is a W8 prerequisite (production must not use container disk; KNOWN_ISSUES).

## D36. Idempotency for retried mutations (resolves D32 gap 4)
Shared mechanism at the RPC/upload layer: the client sends `Idempotency-Key` (UUID) on mutating calls. Table `idempotency_keys(organization_id, user_id, key)` stores command, request SHA-256, response status and body, and an expiry (24 h). The key row, the business change and the stored response are written in **one transaction**: the dispatcher opens it, the handler runs on a scoped connection whose `tx()` nests as savepoints, and a concurrent duplicate waits on the key's primary key, then replays.
- Same key + same command + same body → the original response is replayed (no second transaction).
- Same key with a different body or command → `STATE_CONFLICT` ("Idempotency key reused").
- Business 4xx outcomes are stored and replayed. Unexpected 5xx outcomes roll back everything (including the key) so the client can retry.
- Commands declare `idempotency: 'required' | 'optional'`. **Required** (W2): `assets.create`, `employees.importCommit`, document uploads. **Planned required**: W4 issue/transfer/return/exit-clearance decisions, W6 approval decisions and goods receipts. Imports are additionally protected by consumable import sessions. Natural unique keys (employee code, asset serial policy) remain as a second line of defence. Other mutations accept an optional key.

## D37. Browser client structure and integration (W3)
- `web/` is a Vite + React app ported from the frozen renderer (screens, components and styles reused). It has no Electron, preload or SQLite dependency. Desktop-only screens were removed (lock, setup wizard, backup, recovery, system info). Hash routing is kept.
- The client calls the real contracts only: `POST /api/v1/rpc/<command>`, the multipart upload routes, and authorized GETs for downloads and exports. There is no duplicate domain logic in the browser, and permission checks in the UI are convenience only.
- Same-origin serving: the API serves `web/dist` when `WEB_ROOT` is set (`@fastify/static` 10.1.5; hashed assets are immutable, `index.html` is `no-cache`). Helmet's CSP covers the page, and unknown paths return a JSON 404. Vite's dev proxy keeps one browser origin in development.
- Session: the HttpOnly cookie only; nothing goes into Web Storage. The client sends activity touches and polls the session; `NOT_AUTHENTICATED` returns the user to sign-in with a notice.
- Every non-read RPC carries a fresh `Idempotency-Key` per user action. After a dropped connection, required-idempotency commands (`assets.create`, `employees.importCommit`, document uploads) are retried once with the same key.
- Errors: the server's safe message plus the correlation reference. Non-envelope responses become a generic message. Network failures say that the outcome is unknown. Pages offer a retry where a read failed.
- Mapping and run instructions: `docs/WEB_CLIENT.md`.

## D39. Allocation, transfer, return and exit-clearance model (W4; resolves B3)
- **Targets:** exactly one of employee, workstation/seat, department, team, pool per assignment (`asset_assignments`: one target column per type, a CHECK that exactly one is set). Physical location is a separate column, defaulted from a workstation target but independently settable.
- **One active assignment per asset:** a partial unique index, `one_active_assignment_per_asset ON asset_assignments(asset_id) WHERE status = 'active'`, is the actual guard; service code also locks rows `FOR UPDATE` in a stable (sorted) order so a batched handover can't deadlock against another. A violation surfaces as `STATE_CONFLICT`, not a raw constraint error.
- **History:** assignments are closed, never rewritten — a trigger forbids updating or deleting a non-active row and forbids changing identity/target on an active one. `asset_movements` is append-only (same pattern as `audit_events`). Transfers close the old assignment and open a new one inside the same transaction.
- **Issue eligibility (TAS §6.4):** active lifecycle + `ready` operational + no active assignment + target/location valid and active. A return never flips an asset back to `ready` by itself — the handover records an outcome (`ready | awaiting_inspection | non_operational`), and `ready` requires both the `allocations.inspect` permission and a non-damaged condition. Editing an asset through `assets.update` cannot bypass an `awaiting_inspection` state.
- **Lifecycle vs. assignment (closes the W2/W3 gap):** `assets.changeLifecycle` now checks for an active assignment and refuses retire/dispose/lost with a message naming the current holder. Loss is never silent: `allocations.reportLost` ends the assignment as `lost` with a reason and actor, then moves the asset to lifecycle `lost`. A reinstated or found asset returns to `awaiting_inspection`, never directly to `ready`.
- **Acknowledgment policy (B3):** `settings.handoverAcknowledgment` ∈ `in_app | signed_receipt | in_app_or_signed`, default `in_app`. In-app records the confirming name and the staff member who witnessed it (`ack_recorded_by`); no drawn signature is required. A signed receipt is an uploaded document (owner type `handover`, purpose `handover`) that acknowledges the handover on attach. `in_app_or_signed` allows either, starting `pending` either way.
- **Exit clearance (TAS §10):** opening a clearance snapshots the employee's *currently* active assignments into `exit_clearance_items`; deactivating/exiting an employee never touches assignments by itself (one open clearance per employee, enforced by a partial unique index). Each item resolves via a normal return (closes the assignment transactionally and updates the item), or is flagged `missing`/`disputed` with a reason (assignment stays active), and only `exit_clearance.approve_exception` can resolve `damaged | missing | disputed` — a missing/disputed approval runs the same explicit loss process as a direct report. Closure is refused while any item is `outstanding | damaged | missing | disputed`.
- **Documents on handovers/clearance items:** `document_links.entity_type` now also accepts `handover` and `clearance_item` (D35's single-type check is replaced). HR (`exit_clearance.view/manage`) sees clearance status and can attach evidence, but has no `allocations.*` permission, so cannot open asset custody detail or receive returns — matching TAS §10's "no automatic IT/financial access" requirement. New permissions: `allocations.view`, `allocations.inspect` (existing `allocations.issue/transfer/return`, `exit_clearance.*` already in the catalog).
- **Idempotency (D36):** issue, transfer, return, acknowledge, inspect, reportLost and every clearance-item mutation plus closure declare `idempotency: 'required'`.

No new infrastructure: `tests/web-e2e/allocations.spec.ts` drives issue/transfer/return/inspect/lost/clearance through the real UI against the same throwaway-PostgreSQL + real-API-process harness as W3, with `rpc()` helpers (not UI) only to arrange fixture state. ## D41. Maintenance tickets and asset operational state (W5, TAS §11)
- **Model:** `maintenance_tickets` (ticket number, fault category, priority, status `open → in_progress → resolved → closed`, or `cancelled`), with `maintenance_ticket_events` as an append-only history (same pattern as `audit_events`/`asset_movements`) — a ticket's diagnosis/work/cost updates are distinct recorded events, never overwritten.
- **Asset linkage:** opening a ticket on an active asset always sets `operational_status = 'under_maintenance'` in the same transaction (resolves TAS §11.2's "updated consistently"). Closing requires a prior `resolve` step and an explicit `resultOutcome` (`ready | awaiting_inspection | non_operational`) chosen at closure — closing never defaults an asset to `ready`. Releasing as `ready` requires the same `allocations.inspect` permission as a normal return/inspection, so one authority governs "is this asset safe to reuse" everywhere.
- **Duplicate-ticket guard (DB-enforced, not just a precheck):** a partial unique index blocks a second `open`/`in_progress` ticket per asset *unless* explicitly marked `justified_duplicate` — a flag only the service sets, and only when the caller holds `maintenance.assign` and supplies a justification. Verified against 5 genuinely concurrent HTTP create requests (exactly one succeeds).
- **Inspection-to-maintenance link (resolves KNOWN_ISSUES W-19):** `allocations.inspect` and `allocations.return` are unchanged (they still just set `non_operational`); the browser now offers "Report a fault now" immediately after either produces that outcome, pre-filling the asset. The two actions remain separate authorized calls (not one combined transaction), so a ticket can also be opened independently, anytime, by anyone with `maintenance.create` — including the `employee` role's existing self-report permission, which has no `maintenance.view`, so ticket detail reads use the same after-write exemption as D39's `getHandover`.
- **Cost fields** reuse `finance.view_cost` (no new permission); a non-finance update to a ticket cannot set a cost but also cannot blank out an existing one (matches `assets.update`'s cost-preservation pattern).
- **New permission:** `audits.verify` only (maintenance needed none; `maintenance.assign`/`maintenance.close`/`finance.view_cost` already existed). Granted to `asset_manager`, `it_technician`, `facilities_manager` alongside `audits.view`.

## D42. Physical audits: frozen baseline, scan-as-observation, discrepancy workflow (W5, TAS §13)
- **Frozen snapshot:** `physical_audits` + `audit_items`. Opening an audit resolves its scope (one of location incl. descendants / category / employee custodian / an explicit asset list, capped at 2000 assets) into `audit_items` rows that copy the asset's *current* location path, condition and custodian label as plain denormalized text/columns at that instant. A later edit to the master asset record never changes these frozen values — verified by editing an asset after opening an audit and confirming the item still shows the original data.
- **A scan is an observation, not an edit:** `audits.verifyItem` takes the asset id (already resolved by the browser via the existing `assets.lookup`) plus the observed location/condition. It classifies automatically: matches the frozen baseline → `verified`; location differs → `location_mismatch`; condition differs → `condition_mismatch`; the operator flags a tag/label problem → `identification_mismatch`; no baseline row exists at all → `unexpected`. An expected item that is never scanned must be explicitly flagged `missing` by a reviewer (TAS §5: never automatic). One row per (audit, asset) is DB-enforced (`UNIQUE(audit_id, asset_id)`), so a race between concurrent scans of the same asset settles to one row, verified with 5 concurrent HTTP requests.
- **Resolution paths:** generic `resolveDiscrepancy` (addressed elsewhere, e.g. a repair already logged); `correctLocation`, a dedicated action that updates the master asset location *and* resolves the item in one transaction, linked by the audit-item id in both the `asset.location_corrected` and `physical_audit.item_resolved` audit events (TAS §5: "link the corrective transaction to the discrepancy"); `acceptException`, formal acceptance without correcting data, gated behind `audits.close` (the same closer-level authority pattern as W4's clearance exceptions) — it never marks an asset lost or disposed itself.
- **Closure:** blocked while any item is `pending | discrepancy_open | investigating`; `closureType` is `with_exceptions` if any item ever carried a discrepancy, else `fully_verified`. Cancelling an open audit is also supported (no master-data effect).
- **Reviewer picker:** `audits.listReviewers`, scoped to users holding `audits.resolve/manage/close`, mirroring W5's own `maintenance.listTechnicians` pattern (and W2/W4's existing habit of never exposing the general `users.list` to non-`users.manage` roles).
- **Document evidence:** `document_links.entity_type` extended to `maintenance_ticket` and `audit_item` (same extension mechanism as W4's `handover`/`clearance_item`).

## D43. Configurable approval-policy versioning model (W6, TAS §12.2)
- **One row per version, not a header+version split:** `approval_policies` carries both the policy's identity (`policy_group_id`, stable across edits) and a specific version's own data (`version`, `min_amount_minor`, `currency`, `prevent_self_approval`, `is_active`) in the same row. Editing a policy inserts a brand-new row with a new `version` and flips `is_current` off the old row, on the new one (`one_current_version_per_policy` partial unique index). `approval_policy_steps` belongs to one specific version id. An `approval_instances` row stores the exact `policy_id` (one specific version) it was created against, so it keeps working against that version's steps forever, even after the policy is edited again — verified in `w6-procurement.test.ts` by editing the policy to a different required role mid-flight and confirming the pending instance's step and eligible-approver set are unchanged.
- **Policy selection at submission:** among current, active policies for the transaction type, pick the one whose `min_amount_minor` (same currency as the request) the request's total still clears, preferring the highest such threshold (most specific); a `NULL` threshold is the catch-all. No match → `STATE_CONFLICT` ("configure an approval policy"), never automatic approval (explicit TAS §12 requirement). Multiple competing policies for the same transaction type are supported by this threshold-ranking rule rather than restricting to exactly one policy per type.
- **Step eligibility, exactly one of two forms:** `required_role_key` (any user currently holding that role) or `required_user_id` (that specific user), enforced by a DB `CHECK (num_nonnulls(...) = 1)`. Revalidated fully at decision time — step order, actor eligibility, instance still pending, and self-approval — against the snapshotted policy, never against whatever the policy looks like *now*.
- **No new permissions:** the existing `procurement.view/create/submit/approve/manage_orders`, `receipts.record`, `suppliers.manage`, `approvals.configure` and `finance.view_cost` already covered every W6 action; confirmed before coding by checking TAS §12 against the existing catalog.

## D44. Purchase orders and goods receipt: locking the authorization ceiling instead of a precheck (W6, TAS §12)
- **Authorized-quantity enforcement:** creating or amending a PO line `SELECT ... FOR UPDATE`s the request item it is drawn from before comparing the already-ordered total (across all non-cancelled orders) plus the new/changed quantity against that line's approved quantity. A concurrent order against the same request item serializes on that lock rather than racing a plain read-then-write, matching the pattern already proven for `one_open_ticket_per_asset` (W5) and the active-assignment partial index (W4).
- **Over-receipt prevention the same way:** receiving a PO line locks that `purchase_order_items` row before reading how much has already been accepted/damaged across all prior receipts; a second concurrent receipt on the same line waits for the first to commit, so it always sees the true remaining outstanding quantity before deciding whether to accept. Verified in `w6-procurement.test.ts` by firing two real concurrent HTTP receipt requests that together would exceed the line's quantity — exactly one succeeds.
- **Outstanding quantity = ordered − accepted − damaged.** A *rejected* quantity does **not** reduce outstanding (TAS §12: "a rejected item must not be counted as successfully available inventory" — rejected goods were never taken into custody, so the line is still owed); a *damaged* quantity does reduce outstanding (the goods did arrive and were taken into custody, just not placed into ready stock).
- **Receiving creates, it never calls, `assets.create`:** the receipt service validates category/model/serial/location inline (reusing the now-exported `resolveAssetRefs` and `issueAssetCode` from `assets.ts`) and inserts the asset row itself, inside the receipt's own transaction. `assets.create` opens its own top-level transaction and re-asserts `assets.create` permission, both wrong for a step that must happen atomically alongside the receipt-item and (for individually tracked lines) per-unit rows under `receipts.record`.
- **Bulk stock did not exist before W6.** `resolveAssetRefs` already refused to let a bulk-tracked category become an individual asset, naming "procurement receipts" as the intended mechanism (a comment present since W2/assets.ts) — W6 adds exactly the minimal ledger that comment anticipated: an append-only `stock_movements` table and a `bulk_stock_balances` running total, written only by goods receipt. This does **not** resolve the open B2 business decision on bulk-category policy generally (allocation/issue of bulk stock remains undefined).
- **Idempotent asset/stock registration:** a partial unique index on `goods_receipt_units(organization_id, asset_id)` and on `stock_movements(organization_id, receipt_item_id)` makes a duplicate registration impossible even if application logic ever re-ran outside the normal `Idempotency-Key` path; the normal path (dispatcher-level `withIdempotency`, same as every W2–W5 mutation) already replays the first outcome on a retried `receipts.create` call.

## D45. Report currency grouping and cost-field authorization (W7, TAS §14.2)
- **Never sum across currencies.** Every report function returns a `CurrencyTotal[]` (`{currency, totalMinor, count}`), one entry per currency actually present in the filtered rows; there is no combined/converted grand total anywhere, because there is no approved exchange-rate policy to justify one (TAS §14.2 is explicit on this). A test seeds one asset in INR and one in USD and asserts the two totals never merge.
- **Cost fields are nulled server-side, not hidden client-side.** Every report row type (`acquisitionCostMinor`, `partsCostMinor`/`laborCostMinor`, `disposalProceedsMinor`, procurement amount fields) is explicitly overwritten to `null` in the service function when `!ctx.actor.permissions.has('finance.view_cost')`, and the currency-total arrays are returned empty rather than computed-then-discarded. The browser never receives a restricted figure that a client-side check merely declines to render (explicit TAS §14 requirement, same principle as D35 for documents).
- **Acquisition cost, maintenance expense, purchase commitment, accepted-receipt value, and disposal proceeds are five separate figures,** computed by five separate queries with five separate meanings; none is added to another to produce a "total spend." The procurement report's received/outstanding value is computed per PO line (`unit_price_minor × quantity`), not per asset or per receipt, so a line split across several partial receipts is still counted exactly once.
- **Missing financial metadata is a flag, not a zero.** An asset with no `acquisition_cost_minor` or no `purchase_date` is marked `missingFinancialMetadata: true` and excluded from the currency totals (which sum only non-null costs); it is never treated as a zero-cost asset, which would silently understate a category's valuation.
- **No depreciation.** `DEPRECIATION_ENABLED = false` (`src/shared/reports.ts`) and no net-book-value figure is computed or exposed anywhere. F1 (depreciation policy: method, useful life by class, residual value, in-service convention, proration/rounding, treatment of additions/disposals, capitalizable costs, management-vs-statutory divergence) remains unresolved — see the Unresolved section below. Implementing depreciation before Finance decides these would mean guessing an accounting policy, which the W7 brief explicitly forbids.

## D46. Report query shape reuses existing patterns; no new reporting framework (W7)
- Every report is a single service function in `services/reports.ts` taking `(c, input, ctx)`, following the exact shape every other list/report function in the codebase already uses (`assertPermission` → `schema.parse` → bounded, parameterized SQL with the existing `Params` helper → paginated `many()` call). CSV export reuses the existing `toCsv` formula-injection guard and the `files.ts` route pattern (`guard` → service call → `recordAudit` → `content-disposition` header) verbatim from the W2 asset-export route; no second CSV writer or export abstraction was introduced.
- **Queries are bounded by construction:** list reports use the existing `page`/`pageSize` (capped at 200) pattern; CSV exports use a flat `LIMIT 20000` (matching the existing `exportAssetRows`'s `LIMIT 50000` precedent, scaled down since report rows carry more joined columns) rather than loading an unbounded result set into application memory.
- **Department attribution for the asset valuation report** resolves only through an asset's *active* assignment to an employee or a department directly (`LEFT JOIN asset_assignments ... LEFT JOIN employees ... LEFT JOIN departments ON d.id = COALESCE(assignment.department_id, employee.department_id)`); custody held via a workstation, team, or pool has no single resolvable department in the current schema and is left blank rather than guessed — documented as KNOWN_ISSUES, not silently approximated.
- **No new permission keys.** `reports.view`, `reports.export`, and `finance.view_cost` already existed in the catalog and already covered the full W7 action surface; confirmed by checking TAS §14/§17 against `src/shared/permissions.ts` before writing any code, same as the W6 confirmation for its action surface.

### Cloud hosting (U4): comparison and recommendation
Compared on the dimensions TAS §7/§21 call out: managed PostgreSQL, container hosting, S3-compatible object storage, TLS, backups, monitoring, data residency, recurring cost, recovery options, operational complexity. All three support every requirement in this spec; the differences are cost, India-region residency, and operational complexity for a small operations team (no dedicated SRE function implied by TAS):

| | Managed containers + managed Postgres + S3 (e.g. a single cloud's App/Container service + its managed Postgres + its S3-compatible bucket) | Self-managed VMs + self-managed Postgres | Small-footprint PaaS (e.g. a managed-container platform with managed Postgres and S3-compatible add-ons) |
|---|---|---|---|
| Operational complexity | Low–medium: provider handles OS patching, Postgres minor upgrades, TLS termination | High: the BPO's own team (or this project) owns OS/Postgres/TLS patching and monitoring | Lowest: provider handles almost everything, including zero-downtime deploys |
| India data residency | Available (pick an India region) | Available (self-hosted in any datacenter/region) | Varies by provider; confirm an India region exists before committing |
| Backups | Automated point-in-time recovery typically included | Must be built (this session's `pg_dump`/`pg_restore` procedure, scheduled) | Automated, usually included |
| Recurring cost at this scale (single org, modest traffic) | Low–moderate | Lowest raw compute cost, but add real engineering-time cost for patching/security | Low–moderate, sometimes a usage-based free tier covers early pilot traffic |
| TLS | Provider-terminated, straightforward | Must be configured (e.g. a reverse proxy with a certificate) | Provider-terminated, straightforward |

**Recommendation: a managed-container platform with managed PostgreSQL and an S3-compatible (or native-S3) bucket, in an India region.** This project's operational profile — one organization, a small user base, no dedicated infrastructure team — favors minimizing operational burden over minimizing raw compute cost. The existing code already supports this directly: `STORAGE_DRIVER=s3` with `STORAGE_S3_ENDPOINT` unset targets AWS S3 itself; set for any S3-compatible alternative (DigitalOcean Spaces, Backblaze B2, a self-hosted MinIO, etc.) without any code change — so the actual provider choice can be deferred to budget/procurement without blocking further engineering work. **This recommendation is not a selection**: provisioning, account creation, and credential issuance require the business owner's explicit authorization and were not performed.

### Password/account recovery (U2)
Documented requirements for whenever this is built: a recovery flow must (a) never confirm or deny whether a given username exists (same response either way, matching the existing login error's generic-message pattern), (b) require email delivery (B7) or an administrator-mediated channel, (c) invalidate any prior recovery token on each new request, (d) force a password change on next sign-in (reusing the existing `must_change_password` mechanism), and (e) be rate-limited at least as strictly as login itself. Until built, `users.resetPassword` (administrator-only) is the only recovery path — acceptable for a single-organization pilot with a reachable administrator, **not acceptable as the sole path for a general production rollout**.

### Malware scanning posture (U3)
No scanner is integrated. Production posture while this remains true: restrict upload permissions (`assets.update`/equivalent attach actions) to trusted internal staff only, do not expose document upload to any party outside the organization, and treat every stored document as "not independently verified safe" in any downstream automation that might execute or render uploaded content. The existing `DOWNLOADABLE_SCAN_STATES` allow-list (`not_scanned`, `clean`) already prevents anything explicitly flagged `pending`/`rejected`/`quarantined`/`scan_failed` from being downloaded — but nothing is ever scanned, so nothing is ever flagged either. This is an explicit residual risk, not a claim of safety.

### Backups and recovery (B6)
**Provisional targets (not business-approved, do not treat as guaranteed):** RPO 24 hours (daily `pg_dump`), RTO 4 hours (time to provision a replacement database and restore the latest dump plus re-point the application). A managed-PostgreSQL provider's built-in point-in-time recovery would improve both substantially if selected (see cloud recommendation above) — these provisional figures assume the simplest possible `pg_dump`-based procedure, documented in `docs/BACKUP_RECOVERY.md`, and were chosen as defensible minimums for a single-organization pilot, not as a target validated with the business owner.
**What was actually tested this session:** a full backup-and-restore drill — `pg_dump --format=custom` of a live database with real data, `pg_restore` into a completely separate, isolated database, and independent verification of the restored copy (row counts, a specific record's data, foreign-key integrity, and that role/permission grants survived) — passes (`tests/server/backup-restore.test.ts`). This demonstrates the *mechanism* works; it does not by itself establish the chosen RPO/RTO are achievable at production data volumes or against a specific managed-provider's backup tooling, which will differ from raw `pg_dump`.
**Object storage backups:** most S3-compatible providers offer bucket versioning/replication; TAS requires this be defined once a provider is chosen. Not configured here (no bucket exists to configure).

### S3-compatible storage (TAS §7.1)
Implemented (`server/src/storage/storage.ts`: `S3Storage`), selected via `STORAGE_DRIVER=s3` (`server/src/config.ts`), with required-field validation at boot (missing bucket/region/credentials fails startup, not a later runtime error). Storage keys are server-generated and validated (`assertStorageKey`, unchanged from D35) regardless of driver, so an S3-specific vulnerability class (arbitrary key/path from client input) is not newly introduced. **Verified** against a local S3-API-compatible test double (`tests/server/fake-s3.ts` + `storage.s3.test.ts`): byte-identical round trip, correct existence/404 semantics, idempotent delete, and storage-key validation — 5/5 passing. **Not verified** against a live cloud provider (no account/credentials available in this session); re-verify against the actually-chosen provider before go-live, per the explicit instruction not to claim a cloud deployment is tested from local containers alone. A read-only `reconcileStorage()` helper is provided for the orphaned-object/missing-file sweep TAS requires; it is not yet wired into a scheduled job (deferred — see KNOWN_ISSUES).

### SQLite → PostgreSQL legacy migration (B5, ARCHITECTURE_V2 §8)
Implemented (`server/src/migration/legacyMigration.ts`, CLI: `npm run server:migrate-legacy`). The legacy schema was read directly from `src/main/database/migrations/000{1,2,3}_*.ts`, not inferred from the old spec — this showed the prototype predates allocations, maintenance, physical audits and procurement entirely, so there is nothing to migrate for those modules (not a gap, an absence). Migrated: departments, locations (hierarchical), employees, asset categories/models, suppliers, assets (with asset-code preserved and the target's code counter bumped past the highest migrated number to prevent future collisions), asset-owned documents (byte-copied and checksum-reverified against the recorded sha256, not merely re-linked), and users with their role assignments. **Deliberately not migrated**, by design: teams/workstations/asset pools (unreferenced by anything else in this schema — skipping them loses no relationship), `audit_events`/`backup_history` (operational history of the old app), `app_settings`/`asset_code_config` (the target organization's own configuration is authoritative), and legacy password hashes (every migrated user gets a fresh random password with `must_change_password = true`, so legacy local authentication can never bypass the server's password policy). Dry-run (`plan`) writes nothing; `apply` is transactional and all-or-nothing per run — any row conflicting with an existing, unrelated target record aborts the entire apply with nothing written, rather than partially applying; a second `apply` on the same source is a no-op (idempotent via a `legacy_migration_records` checkpoint table) rather than a duplicate. `verify` independently re-checks counts, referential integrity, and asset-code uniqueness on the target after an apply. ### C1 — Lease-enforcement architecture: recommended design
Inspected every mutation path named in the prompt. Finding: **almost every one already takes a `SELECT ... FOR UPDATE` row lock on its primary entity before mutating** — this is the existing, proven invariant-enforcement idiom used consistently since W4 (D-series decisions already call this pattern out for `one_open_ticket_per_asset`, PO/receipt ceilings, etc.). There is, however, **no single shared function spanning all six service modules** — each module locks its own tables independently:

| Mutation path | File | Existing lock point (the lease check's natural insertion point) |
|---|---|---|
| Lifecycle changes | `assets.ts: changeLifecycle` | `SELECT ... FROM assets ... FOR UPDATE` |
| Issue/transfer/return/inspect/report-lost | `allocations.ts` | Shared internal helper that locks `assets` `FOR UPDATE` (reused across these five functions already — the one genuine existing shared choke point) |
| Maintenance create/assign/update/resolve/close | `maintenance.ts` | Per-function `SELECT ... FROM maintenance_tickets ... FOR UPDATE` (and the asset row for `createTicket`) |
| Audit verify/flag/assign/resolve/correctLocation/acceptException/close | `audits.ts` | Per-function lock on `audit_items`/`physical_audits`. **Gap found:** `correctLocation` (the one discrepancy-resolution path that mutates `assets.location_id`) reads the asset row *without* `FOR UPDATE` before updating it — pre-existing, independent of W9, but exactly the kind of path a lease check must not miss; flag for a lease-enforcement test specifically, and consider adding the lock as ordinary hardening regardless of W9. |
| PO creation/amendment, receipts | `purchasing.ts` | `SELECT ... FROM purchase_order_items ... FOR UPDATE` / `FOR UPDATE OF i` |
| Request-level ceilings | `procurement.ts` | `SELECT ... FROM purchase_request_items ... FOR UPDATE` |
| Asset-code issuance/config | `assets.ts: issueAssetCode` / `updateAssetCodeConfig` | Both already lock the *same* `asset_code_config` row — see C3 |
| Legacy migration | `legacyMigration.ts` | No row-level locks today (bulk inserts under one transaction) — see decision F |

**Recommendation: application-service enforcement at each of these existing lock points, not a database trigger as the primary mechanism.** A trigger was considered and rejected as the *primary* mechanism because: (a) it requires every legitimate bypass — the lease-holder's own sync-accepted write — to carry a session-scoped marker that nothing currently sets, which is itself a change at every one of the same call sites, so a trigger does not actually avoid auditing them; (b) the request-level and asset-code-range invariants (C2, C3) are quantity/counter math a trigger cannot evaluate without duplicating the service-layer logic in PL/pgSQL. The honest trade a trigger buys is defense-in-depth against a *future* mutation path someone adds without knowing about leases — worth doing **once the lease/reservation tables exist**, as a second layer on `assets` and `asset_assignments` specifically (the two highest-value, most-mutated tables), but it must not be sold as sufficient on its own, and does not remove the obligation to add the explicit check at each table above.

Concretely: one new shared helper (e.g. `assertNotLeased(t, org, entityType, entityId)` in a new module, not written in this task) called immediately after each existing `FOR UPDATE` in the table above. This is a **finite, enumerated** list of call sites (nine functions/files), which is exactly what the prompt asked for instead of an unproven blanket claim.

### C3 — Asset-code range reservations: locking protocol
`issueAssetCode` and `updateAssetCodeConfig` already lock the **same** `asset_code_config` row (`org`-keyed, `FOR UPDATE`) before reading/writing `next_number` — confirmed by reading both functions. This means a range reservation slots in cleanly: **reserve-a-range is a third operation that takes the same row lock, bumps `next_number` by N in one step (instead of 1), and records the reserved range `[start, end)` plus the device/lease ID and the `(prefix, separator, padding)` triple in effect at reservation time in a new table** (not created in this task). Because all three operations (`issueAssetCode`, `updateAssetCodeConfig`, reserve-a-range) serialize on the one row lock, there is no race between normal online issuance and an offline range reservation by construction — no new locking primitive is needed, only a new row-lock-holding operation using the existing one.
- **Format changes must be blocked while any reserved range has unused numbers remaining.** `updateAssetCodeConfig` must be extended to check the new reservation table for any range with `(reserved_end - consumed) > 0` before allowing a prefix/separator/padding change, under the same lock it already holds — this is a small, well-scoped addition to an existing, already-locked function, not a new subsystem.
- **Numbers are never reused**, including a range's unused tail when a device never returns: the range stays burned (gap), exactly as TAS §4.3/§7.4 already specify. A reservation's "unused tail" is released from the *reservation* (so a future range can start past it) only through the same audited reconciliation/force-reclaim procedure as any other lease, never by silently recycling the numbers.
- Reservation issuance and its audit record must be written in the same transaction as the counter bump — mirroring the existing `issueAssetCode`/audit pattern exactly.

## D50. W9.2 server-side foundations implemented (device enrollment, exclusive leases, asset-code ranges)
Implements the D49-approved policy (A–G) at the server/database layer, exactly as scoped: device enrollment/trust/revocation, exclusive PostgreSQL-backed leases on either an asset scope or an asset-code-range scope, the nine online-write enforcement checkpoints, asset-code range reservation sharing the existing `asset_code_config` row lock, force-reclaim restricted to a separate recovery authority, and the legacy-migration guard. **No synchronization protocol, local outbox, offline command execution, or new UI screens exist** — this is the server API/CLI foundation a future desktop agent will consume, not the agent itself. All of the following is verified against a real, ephemeral PostgreSQL database with real concurrent HTTP requests (`tests/server/w9-offline-leases.test.ts`, `tests/server/legacy-migration.test.ts`); nothing here is asserted from a mock.

### What is implemented and tested now
- **Device enrollment/trust/revocation** (`sync_devices`): a user self-registers a device (`pending`); only `devices.manage` (Super Admin by default) can approve it, and approval requires non-empty `trust_notes` recording what was actually verified — never a self-reported client flag (D49/B). A device cannot approve itself. Revoking a device force-reclaims any lease it still holds in the same transaction, since there is no live connection to push a revoke signal to (tested).
- **Exclusive leases** (`offline_leases` + `offline_lease_scopes`): `requestLease` grants an `asset` or `asset_code_range` scope for up to `MAX_LEASE_HOURS` (8, D49/A) to an active, trust-approved device owned by the caller. A PostgreSQL partial unique index (`one_active_lease_per_asset`) — not an app-level precheck alone — is the actual mechanism that rejects an overlapping asset lease; this is proven with five real concurrent HTTP requests racing for the same asset, exactly one of which wins (tested).
- **C1 — online-write protection:** `assertAssetsNotLeased` is wired into every enumerated asset-mutating entry point: `allocations.ts`'s shared `lockAssets` (covers issue/transfer/return/inspect/reportLost), `assets.changeLifecycle`, `maintenance.createTicket` and `closeTicket`, and `audits.correctLocation`. The block is unconditional — it applies even to the lease's own holder acting through the browser, since allowing that would let them race their own not-yet-synced offline work (D49, explicit design decision made in this phase; tested both ways).
- **Two pre-existing locking gaps found and fixed while wiring C1** (same class of correctness issue the prompt specifically asked to check): `audits.correctLocation` read the asset's location with a plain `SELECT`, then wrote it with an unlocked `UPDATE` — fixed to `FOR UPDATE`. `maintenance.closeTicket` mutated `assets.operational_status` without ever locking the asset row (only the ticket was locked) — fixed the same way.
- **C2 — procurement stays online-only:** no lease-check calls were added to `purchasing.ts`/`procurement.ts`, by construction, not omission — `offline_leases.scope_type` only allows `'asset'`/`'asset_code_range'`, so there is structurally no procurement-scoped lease that could ever conflict with a procurement mutation.
- **C3 — asset-code range reservation** (`reserveAssetCodeRange` in `assets.ts`, `asset_code_reservations` table): locks the *same* `asset_code_config` row `issueAssetCode`/`updateAssetCodeConfig` already lock, so a reservation can never race normal online issuance or a format change. A format/prefix change is blocked while any reservation's owning lease is `active`/`expired` (tested: reservation reserves a contiguous range, online issuance continues past it, format change is refused while outstanding and allowed once released).
- **D49/E — force-reclaim:** `leases.force_reclaim` is a separate, Super-Admin-only permission; `forceReclaimLease` hard-rejects (`PERMISSION_DENIED`) whenever the caller is the lease's own holder, even if they hold the permission — tested with a `super_admin`-roled user attempting to reclaim their own lease.
- **D49/F — legacy migration guard:** `applyLegacyMigration` checks for any `active`/`expired` lease in the target organization before writing anything and aborts (reporting which device is blocking it) exactly like its existing "stop and report conflicts, never partially apply" design; `planLegacyMigration` (dry-run) is unaffected since it never writes (tested).
- **Fencing epoch** (`fencing_epoch_seq`): every granted lease gets a real, monotonically increasing epoch today. Expiry is materialized lazily on read/mutate (no scheduler exists in this codebase) and — per D49's "expiry does not automatically release the reservation" — never clears `is_active` on the lease's scopes; only an explicit release or reclaim does.

### What remains an explicitly documented gap, not a tested guarantee
- **D49/G, backup/restore vs. the fencing epoch:** only the safe prerequisite (the real `fencing_epoch_seq` sequence) is implemented. A fully automated cross-restore-safe watermark would require storing state outside the routine `pg_dump`, which is an infrastructure decision beyond this phase's server-code scope. The manual operational step (record the sequence's value before a restore, advance it past every epoch issued since the backup, before any new lease is granted) is documented in `docs/BACKUP_RECOVERY.md`; a diagnostic CLI helper is planned, not built.
- No synchronization protocol, local outbox, offline command execution, or new UI screens exist (explicitly out of scope per the W9.2 brief) — every acceptance criterion in D48 that requires two real desktop agents (concurrent competing requests from two physical agents, outbox restart-without-duplication, full sync-protocol idempotency under induced failures) remains untested and cannot be tested honestly until that agent exists. Nothing in this phase's test suite simulates that with mocks.

## D52. W9.7 offline-sync ingestion implemented, gated off by default (W-44/W-45 unresolved)
Server-side commands exist that turn a desktop agent's locally-pending audit observations and maintenance requests into real, authoritative server records (`offlineSync.uploadObservation`, `offlineSync.uploadMaintenanceRequest`) — the first write path a disconnected device can ever reach. Per the explicit instruction to "implement only the safe portions and keep unsafe upload paths disabled" when a prerequisite is unresolved: both `offlineSync.uploadObservation` and `offlineSync.uploadMaintenanceRequest` check a new `SYNC_UPLOADS_ENABLED` server config flag (`server/src/config.ts`), **defaulting to `false`**, and refuse every upload with a clear error naming W-44/W-45 while it is off. Turning it on is a deliberate operational action, not a default; nothing in this change makes it true automatically.

### Why gated, precisely
- **W-44 (fencing not restore-safe) is unresolved.** The new commands validate the client-supplied `fencingEpoch` against the lease's real, current row value — this rejects a record created under a lease that has since been reclaimed and re-granted (a normal, common case) but does **not** close the narrow restore-replay gap already documented in W-44/`docs/BACKUP_RECOVERY.md`: a restored sequence could in principle reissue a stale epoch value. The epoch check is necessary and tested; it is not claimed to be sufficient against that specific scenario.
- **W-45 (device trust is attestation-only) is unresolved**, per D51's own finding — no business owner has accepted attestation-only trust as sufficient, and this change does not treat it as accepted. Sync uploads inherit the exact same device-trust dependency every lease already has (a lease cannot exist on an unapproved device); nothing here makes that assumption any stronger or weaker.
- **Revocation/force-reclaim were not assumed to prevent a physical action taken while disconnected.** Revoking a device already force-reclaims its leases (W9.2); the new check here only confirms that a reclaimed/released lease's records are refused at *upload* time — it says nothing about, and does not claim anything about, what a disconnected device may have already done locally before reconnecting.

### What is implemented and tested (independent of the gate — the mechanism itself is correct and exercised)
- Authorization is derived entirely from real server state, never from client-supplied values alone: `leaseId` is looked up fresh; the lease's actual `user_id`, `device_id`, `status`, `scope_type`, and `fencing_epoch` are cross-checked against what the client claims, and `offline_lease_scopes` is checked for real asset-scope membership. A mismatch anywhere — wrong user, wrong device, wrong epoch, out-of-scope asset, or a lease that is `released`/`reclaimed` — is rejected.
- **Observations** get a new, honestly-named table (`offline_observation_records`) rather than being forced into the unrelated `physical_audits`/`audit_items` shape (which models a server-opened audit with its own frozen snapshot — an offline observation was never opened against one). **Maintenance requests** reuse the real `maintenance.createTicket` service directly (same permission check, same duplicate-open-ticket guard, same audit trail) — the one genuine domain-service reuse this phase's data allowed. Reusing `createTicket` surfaced a real, correct enforcement collision: C1's `assertAssetsNotLeased` guard (W9.2) by design blocks `createTicket` on a leased asset — which the synced ticket's own asset always is. Fixed with a narrow, explicit exception (`assertAssetsNotLeased`'s new `allowLeaseId` parameter): only `offlineSync.ts` passes the lease it has already verified authorizes this exact write; every other caller is unaffected and the guard still blocks every ordinary online actor unconditionally.
- **Two independent duplicate-prevention layers**, not one: the existing idempotency-key machinery (D36, 24h TTL) for the common fast-retry case, using the client's own stable local-record id as the key; and a new, permanent `offline_sync_uploads` table (UNIQUE on `(organization_id, client_record_id)`) for a retry arriving after that window — a disconnected agent may reasonably reconnect days later. A race on the permanent table (two concurrent requests for the same `client_record_id`) is treated as a successful duplicate, not an error, by re-reading the winning row.
- Partial-failure isolation is structural, not a special code path: each upload is its own independent command/transaction, so one rejected record cannot affect any other — proven with a test uploading a bad record between two good ones.

### Verified
10 new server tests (`tests/server/w9-offline-sync.test.ts`) against real PostgreSQL: the gate refuses an otherwise-valid upload while off; a valid observation and maintenance request succeed once enabled, the latter producing a real ticket; wrong-scope asset rejected; stale epoch rejected; revoked-lease upload rejected; invalid payloads rejected; same-key retry replays the cached response; different-key retry for the same client record still returns the original entity, not a new one, for both record types; partial-batch isolation. Full regression: typecheck (6 projects), `test:server` 134/134, `tests/agent`/`prototype`/`web` 185/185 unaffected.

### Not done in this phase
The desktop agent does not yet call these endpoints — no `cloud.*`/dispatcher wiring was added on the agent side. Phase B's brief scoped this task to server-side ingestion only; agent-side sync triggering is a distinct, later piece of work.

## D55. Bulk asset import (CSV/Excel), closing K19 — individually-tracked categories only, modeled on the W2 employee importer
The cloud app had an employee CSV importer (W2) but no equivalent for assets (KNOWN_ISSUES K19, open since M3). Built a parallel asset importer, deliberately copying the employee importer's proven shape rather than inventing a new one: an owner-bound, expiring `import_sessions` row (migration `0009_asset_import.ts` widens its `kind` CHECK from `'employees'` to `('employees', 'assets')`) holds the parsed file as `jsonb`; `assets.importPreview`/`importCommit`/`importCancel` (new W2 RPC commands, `assets.import` permission, granted by default to `asset_manager`) re-validate against *current* data at both preview and commit time via a pure function (`server/src/imports/assetValidation.ts`) over pre-loaded, organization-scoped lookups; commit runs in one transaction, re-validates, and is all-or-nothing unless the caller explicitly sets `skipInvalidRows`.

**Scope decisions, confirmed with the project owner before implementation:**
- **Individually-tracked (serialized) categories only.** A row targeting a bulk/quantity-tracked category is rejected with an explicit message ("recorded through procurement receipts, not through import") — bulk stock has its own, different creation path (W6) and was never going to be reconciled correctly against row-per-unit CSV semantics.
- **CSV and Excel (.xlsx), not CSV-only.** D19 (M2) had already evaluated `.xlsx` libraries for the historical prototype and picked **read-excel-file** (pinned `9.3.12`, re-verified current on npm before adding it as a `dependencies` entry, not `devDependencies` — it runs server-side). A multi-sheet workbook (the real-world case: one sheet per asset type) asks the caller to choose a sheet via a `needsSheetSelection` response from the upload route before anything is parsed into a session; the client re-uploads the same file with `?sheet=<name>`. Excel date cells are converted directly to `YYYY-MM-DD` (no DD/MM-vs-MM/DD guessing — Excel already stores an unambiguous calendar date), unlike CSV text dates, which still require the existing explicit date-format picker.
- **New `assets.import` permission, not reuse of `assets.create`.** Mirrors how `employees.import` is distinct from `employees.manage` — bulk-importing hundreds of rows is a different risk profile from creating one asset, and the two are independently revocable.
- **Asset codes are never read from the file.** Every imported row gets its code from the same `issueAssetCode()` the single-asset-create path uses, inside the same transaction — consistent with "asset_code is immutable, server-issued" (CLAUDE.md) and explicitly different from the employee importer, where the Employee ID *is* supplied by the file (employees don't have a server-issued identity scheme).
- **Category/location/supplier resolved by name-or-code against existing catalogue rows, never auto-created** — identical convention to the employee importer's department/team/location resolution. Manufacturer/model are free text on the imported row (no model-catalogue matching attempted); this exactly mirrors creating one asset by hand without picking a catalogue model, not a new allowance.
- **Acquisition cost gated by `finance.view_cost` at the file-mapping level**, not silently dropped per row: if the actor lacks the permission and still maps that column, the whole file is blocked with one clear message, rather than importing everything else and silently zeroing cost — avoids a surprising, hard-to-notice partial outcome.

**Reused, not reimplemented:** `resolveAssetRefs`'s category/serial-uniqueness business rules are *not* called directly (that function throws on first error and hits the DB per call); instead `validateAssetImport` independently encodes the same rules as a pure, pre-loaded-lookup function, exactly as `employeeValidation.ts` already does relative to `employees.ts` — collecting every field's issues per row instead of stopping at the first. `assets.ts`'s `baseCurrency`/`parseCost`/`issueAssetCode` *are* exported and reused directly for the actual money/code logic, since those have no row-collection concern.

## D56. Browser camera QR scanning added to the Scan page (TAS §8.2, partially resolves U5)
TAS §8.2 asked for "browser camera scanning for QR codes where supported," explicitly "behind a controlled capability check," with USB and manual search remaining the baseline. Added a "📷 Scan with camera" option to the existing `ScanPage.tsx` using the native **Barcode Detection API** (`window.BarcodeDetector`) plus `navigator.mediaDevices.getUserMedia` — zero new dependencies. `cameraSupported` is computed once from `!!navigator.mediaDevices?.getUserMedia && !!window.BarcodeDetector`; the button, and all camera UI, simply don't render when either is missing (Firefox and Safari today), leaving USB/manual entry completely unaffected — this *is* the "controlled capability check" the spec asked for. A decoded QR payload is fed through the exact same `submit()` path as a USB scan or typed entry, so it reuses `assets.lookup` unchanged: no new server code, no new way to mutate anything (the spec's "a scan must not issue/return/transfer/dispose..." requirement was already satisfied by the existing lookup-only design and still is).

**A real race condition found and fixed during testing, not just a flaky test:** the first implementation scheduled `requestAnimationFrame` immediately after `setCameraOpen(true)` to grab the just-rendered `<video>` element, assuming the rAF callback would run after React's commit. It doesn't reliably — rAF can fire before React mounts the element, silently leaving `videoRef.current` null, aborting detection setup with no error shown, and leaving the UI stuck showing "camera open" with nothing happening. Fixed by moving the stream-attach-and-detect logic into a `useEffect` keyed on `cameraOpen`, which React guarantees runs only after the DOM commit — eliminating the race rather than papering over it with a longer delay.

**Verified (original, native-`BarcodeDetector` version):** `npm run typecheck` (5 projects) clean. New `tests/web-e2e/cameraScan.spec.ts` exercises the real pipeline, not a fully mocked one — Playwright's Chromium is launched with `--use-fake-device-for-media-stream`/`--use-fake-ui-for-media-stream` and a real `camera` permission grant, so `getUserMedia` and the `<video>` stream are genuine; only `BarcodeDetector` itself is stubbed, since this Chromium build has no on-device barcode-detection model (`typeof window.BarcodeDetector` confirmed `undefined` by direct check before stubbing). One test confirms end-to-end: camera opens, decodes a QR payload, resolves the same asset a USB scan would, and the camera stops itself. A second confirms the capability check: deleting `window.BarcodeDetector` removes the camera button entirely and shows the USB/manual fallback message. ### Follow-up: native `BarcodeDetector` replaced with `jsqr` — the user hit the capability gate immediately in real use
The user tried the feature in their actual browser and got "Camera scanning isn't available on this browser or device" — the capability check was doing exactly what it was built to do, but the native Barcode Detection API it gated on turns out to have near-zero real-world availability: it's absent from most desktop Chrome installs (model download/flag-gated), and never implemented at all in Firefox or Safari. A "controlled capability check" that's almost always false isn't a working feature; it's the feature turned off. Replaced the decoder with **`jsqr`** (`1.4.0`, Apache-2.0, zero dependencies, actively maintained — verified on npm before adding, added to `devDependencies` alongside `react`/`vite`, matching this repo's existing convention that client-bundled runtime libraries live there rather than in `dependencies`, which is reserved for what the server's own Node process requires). `jsqr` decodes from raw canvas pixel data (`Uint8ClampedArray` + width/height), so it works anywhere a `<canvas>` 2D context does — which is universal — rather than depending on a specific, inconsistently-shipped browser API. `cameraSupported` now checks only `navigator.mediaDevices.getUserMedia`; the detection loop draws each video frame to an offscreen `<canvas>` on a 200ms interval, reads it back via `getImageData`, and calls `jsQR(data, width, height)`. ## D59. Generic reference-data CSV/Excel import for categories, models, suppliers, departments, teams, locations and workstations
The user had existing data for the organization's catalogue/structure and could not add it one record at a time. Scoped with the user as a **one-time bulk-setup** need (not a recurring workflow), which settled the architecture question in favor of **one shared, generic import engine** reused across all seven entities, rather than seven bespoke wizards (the shape the existing Employee/Asset importers use, each with their own validator and UI). The two existing importers remain untouched and un-generalized — they carry entity-specific complexity (manager-loop detection, server-issued asset codes, cost/currency handling) that a shared engine would only have complicated.

**Shared engine, not shared type reuse:** `src/shared/referenceImport.ts` defines the seven kinds, each one's column list (key/label/required) and its permission gate (`reference_data.manage` for categories/models, `suppliers.manage` for suppliers, `locations.manage` for departments/teams/locations/workstations — the same permission creating one by hand already requires, so import adds no new permission). `server/src/imports/referenceImport.ts` is one engine: a lookups loader (categories/departments/locations, needed as parent references), a per-kind `resolveRow` switch producing a typed `ResolvedRow` union, a generic in-file-plus-DB duplicate-detection pass driven by each kind's own uniqueness dimensions (e.g. a category is unique by code *and* independently by name, matching `checkCategoryUnique`'s two separate checks — a single combined natural key would have been wrong), and a per-kind `insertReferenceRow` switch for the actual `INSERT`. **Scope deliberately narrower than the Employee/Asset importers, by design for a one-time bulk-setup tool:**
- **Parent references (category for a model, department for a team, location for a workstation or a location's own parent) resolve only against records that already exist** — never auto-created, and never resolved against other rows in the same file. - **No manager/lead assignment via import** (department manager, team lead) — deliberately left to the existing single-record edit screens, consistent with treating import as filling in the structure, not every optional relationship.
