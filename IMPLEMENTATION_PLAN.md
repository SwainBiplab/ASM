# Implementation Plan: BPO Asset Management System v1 (cloud web application)

**Specification:** `BPO_ASSET_MANAGEMENT_TAS_v2.0.md` (authoritative; roadmap = §22, acceptance = §21, traceability = §24). Rationale and migration matrix: `docs/ARCHITECTURE_V2_CLOUD.md`. Historical desktop spec: `BPO_ASSET_MANAGEMENT_TAS_v1.0.md`. The previous standalone plan is in git history (`3e13749:IMPLEMENTATION_PLAN.md`).
Each phase ends with: focused + regression tests, security review, tracking-doc update, separate commit.

## Baseline
React + TypeScript browser UI · Fastify + TypeScript API with parameterized plain SQL · PostgreSQL · S3-compatible document storage behind an abstraction · centralized server-side sessions · one container + managed PostgreSQL + object storage (provider undecided, U4) · one BPO organization initially; multi-tenant SaaS only after separate isolation and security work · no full offline synchronization (U1 open; provisional online-only policy, TAS §2.3).

### W1: Server foundation (complete)
Delivered: Fastify app factory, validated config, `pg` layer, checksummed migrations with an advisory lock, migration 0001 (organizations, identity/RBAC with organization-scoped FKs, hashed-token sessions, settings, append-only audit), scrypt, lockout + login rate limit, idle (setting, default 15 min) and absolute (12 h) expiry, revocation, CSRF header + Origin check, helmet CSP, safe errors, health, operator CLI, ephemeral PostgreSQL test harness. Not verified: TLS proxy/`__Host-` cookie behaviour, deployment, storage, browser UI.

### W2: Business modules on PostgreSQL/API (complete)
Scope (TAS §22 W2): departments, teams/processes, locations, workstations/seats, pools, employees; CSV preview/validation/atomic import; categories, models, suppliers, assets, code generation (row-locked counter, B1/D20), lifecycle data, documents, labels, scanning lookup, search, exports; upload/download endpoints; storage abstraction (local driver for dev/test; S3-compatible driver interface).
Also required by TAS v2.0 and recorded in D32 (resolve at W2 start, before porting modules):
- API versioning policy or versioned prefix (§3.4).
- Response schemas/serialization for every route, including field-level restriction of cost and personal data (§3.4, §24).
- Explicit schemas on non-RPC routes (uploads, downloads, exports).
- Document metadata with organization ownership, scan status and cross-organization link tests (§7.1); uploads not described as malware-safe while U3 is open.

Exit criteria (TAS): modules have server persistence and tests, authorization is enforced, document storage access is protected, migration/invariants pass, and the schema/API can support W3. **All met** (see PROJECT_STATUS). Carried forward: S3 driver (W8), SQLite→PostgreSQL data migration tool (W8), server-side demo seeder for development (W3 convenience).

### W3: Browser application integration (complete)
Connect the React screens (reused from `src/renderer`) to the API through a typed HTTP client; central sign-in/session lifecycle and error handling; uploads and downloads; role-specific UI with server-side field authorization; browser E2E. Exit: no core flow relies on prototype/SQLite; essential workflows pass browser E2E. **Met:** `web/` has no Electron or SQLite path; 25 Chromium E2E tests pass against the real API + PostgreSQL (see PROJECT_STATUS). Carried forward: cross-browser checks and an accessibility audit (W7), TLS/cookie verification (W8).

### W4: Allocation, transfers, returns and exit clearance (complete)
Assignment targets, active-assignment constraint (partial unique index + row lock), assignment and movement history, handover acknowledgment (B3: in-app by default; printable or attached signed receipt where required; method configurable), return inspection, employee clearance and exceptions, idempotency for retried mutations (D32). Fix the prototype issue where assets could be retired, lost or disposed while assigned. Exit: no duplicate active assignment under concurrent requests; custody workflows auditable and validated through browser/API tests. **All met** (D39–D40, see PROJECT_STATUS): the partial unique index plus row locking was verified with genuinely concurrent HTTP requests (5-way race, exactly one winner); `assets.changeLifecycle` now refuses retire/dispose/lost on an assigned asset and names the holder; loss is always explicit (`allocations.reportLost`, or an approved clearance exception) and never closes an assignment silently. Carried forward: notifications for overdue returns, a maintenance-ticket link from a failed inspection (both W5), and clearance coverage of non-direct custody relationships (TAS §10.2, open product question in DECISIONS.md).

### W5: Maintenance and physical audit (complete)
Maintenance tickets (fault category, priority, status history, technician assignment, vendor/cost/downtime, authorized return-to-service decision at closure) and physical audits (frozen expected-inventory snapshot at open, scan/lookup verification, discrepancy classification and resolution, formal exception acceptance, closure). Resolves the W4-era gap (KNOWN_ISSUES W-19) linking a failed inspection to a new maintenance ticket. **All met** (D41–D42, see PROJECT_STATUS): the duplicate-ticket and one-row-per-audit-item invariants are DB-enforced (partial unique index / unique constraint) and verified under genuine concurrency; closing a ticket never defaults an asset to ready; an audit's baseline is immune to later master-data edits; a location discrepancy's correction is linked to its master-data update in one transaction. Carried forward: overdue-ticket notifications (W7), non-direct custody in audit/clearance scope (open product question), audit item-list pagination in the browser (W7).

### W6: Procurement, configurable approvals, purchase orders, goods receipt (complete)
Purchase requests (draft/submit/approve-reject/cancel), a versioned configurable approval engine (role-or-named-approver steps, optional amount threshold, self-approval prevention, policy edits never retroactively altering an in-flight instance), purchase orders locked to a request's authorized quantities with an audited amendment trail, and goods receipt as a workflow distinct from approval (partial deliveries, damaged/rejected discrepancies, DB-locked over-receipt prevention). Accepted receipt lines register individually tracked assets or bulk stock movements, idempotently on retry. Exit: no procurement operation bypasses server authorization or the configured approval route; concurrent approval/order/receipt attempts cannot violate quantity or decision invariants; browser screens cover every workflow with real API data. **All met** (see PROJECT_STATUS): 4 new server tests (97/97 total) cover self-approval blocking, mid-flight policy-version isolation, authorized-quantity enforcement, asset/stock registration correctness, idempotent retry, and concurrent over-receipt; 6 new browser E2E tests (48/48 total) cover the full golden path end to end. Carried forward: PO-amendment re-approval (amendments are audited but do not restart the approval chain — explicitly out of scope per the prompt), warranty dates on receipt-created assets (no duration source yet on category/model), a model picker on request/order lines (category only).

### W7: Financial and management reporting (complete)
Asset acquisition/valuation, maintenance expenditure, procurement and receiving traceability, warranty/lifecycle, and disposal reports, all currency-grouped integer-minor-unit calculations against real PostgreSQL records, with `finance.view_cost` hiding cost/proceeds fields server-side (not just in the UI) and `reports.view`/`reports.export` gating every command and CSV route. Depreciation remains explicitly disabled pending F1. Exit: reports reconcile to known fixtures; no cross-currency totals; exports preserve on-screen authorization; no unapproved depreciation presented as authoritative. **All met** (D45–D46, see PROJECT_STATUS): 6 new server tests (105/105 total) independently verify currency separation, date-range filtering, cost hidden end-to-end, maintenance/procurement/disposal totals, and CSV formula-injection/organization-isolation; 4 new browser E2E tests (52/52 total) verify the same through the UI. Carried forward: a department dimension for non-employee/non-department custody (workstation/team/pool), CSV export of the procurement aggregate tables (only the discrepancy list exports today), depreciation itself (blocked on F1).

### W8: Production deployment, legacy migration, pilot readiness (complete, blockers documented)
As defined in TAS v2.0 §22: provider selection (U4), staging deployment, TLS/cookie verification, backup and document recovery drills (B6), SQLite→PostgreSQL dry-run/apply/verify data migration (ARCHITECTURE_V2 §8, B5), pilot and sign-off. Exit criteria per the brief: a production-compatible deployment configuration exists, the storage driver passed integration testing, the migration tool dry-runs/validates/applies/verifies safely, backup/recovery passed isolated restoration testing, required tests pass, and unresolved decisions are documented with no overstated readiness claim. **All met** (D47, see PROJECT_STATUS): S3-compatible storage driver (tested against a local S3-API-compatible test double, not a live provider), SQLite→PostgreSQL migration tool (plan/apply/verify, transactional and all-or-nothing on conflict, idempotent via a checkpoint table, tested against a real legacy-schema fixture built from the prototype's own migrator), a portable container deployment (Dockerfile + compose, syntax-validated, not yet built/run — no Docker daemon in this environment), a documented backup/recovery procedure with a real `pg_dump`/`pg_restore` drill independently re-verified, and a classification of every open decision (U1–U6/F1/B1–B7) into resolved/deferrable/must-decide/needs-business-decision. 8 new server tests (113/113 total). Production launch remains subject to formal approval and is explicitly **not** claimed ready: cloud provisioning (U4), email delivery (B7), and self-service password recovery (U2) all remain undecided or unbuilt, and nothing was verified against a live cloud provider or a real TLS proxy.

### W9 (offline): fully retired — desktop agent removed (D53), server-side offline infrastructure removed too (D54)
W9.0/W9.1 approved a controlled-offline design (exclusive leases, local outbox, fencing-token conflict rejection) via an Electron desktop agent (DECISIONS.md D48/D49). W9.2 built the server-side foundations (device enrollment/trust/revocation, exclusive leases, asset-code ranges, online-write protection — D50) and W9.3–W9.6 built the desktop agent itself. The project owner then changed the product direction to cloud-only (D53: removed `agent/`, its build/test tooling, `src/shared/clientApi.ts`), and has since decided to drop the offline feature entirely rather than keep its server-side half waiting for a client that will never exist (D54).

**D54 removed:** `offlineLeases.ts`/`offlineSync.ts`, migrations `0009`/`0010`, the `devices.*`/`leases.*`/`offlineSync.*` commands, the C1 `assertAssetsNotLeased` write-protection in `allocations.ts`/`assets.ts`/`maintenance.ts`/`audits.ts`, asset-code-range reservation support (`reserveAssetCodeRange`, `format_version`), the three offline-only permissions, and the "Offline agents" admin web screen. **No offline/lease/sync capability of any kind exists in the codebase today.** The two W9 planning documents are kept as historical design record, marked superseded. See DECISIONS.md D48–D54 for full detail.

### W2 extension: bulk asset import (CSV/Excel), closing K19 (D55)
W2's original scope (line above) shipped a CSV employee importer but no asset equivalent (KNOWN_ISSUES K19). Added `assets.importPreview`/`importCommit`/`importCancel` and a web wizard, modeled directly on the employee importer's shape (owner-bound expiring session, pure re-validation at preview and commit, all-or-nothing commit unless rows are explicitly skipped). Scope: individually-tracked categories only (a bulk/quantity-tracked row is rejected — that stock arrives through procurement receipts); CSV and `.xlsx` (new `read-excel-file` dependency, pinned per D19's prior evaluation), with a sheet-choice step for multi-sheet workbooks; asset codes always server-issued, never read from the file; a new `assets.import` permission distinct from `assets.create`. Full rationale and verification in DECISIONS.md D55.
