# Known Issues and Limitations

> Since the architecture change (D24), issues K1–K23 refer to the **Electron prototype** unless restated below. Web-app issues use the W prefix.

| ID | Area | Description | Plan |
|---|---|---|---|
| W-1 | Web | Browser UI connected (W3). Automated browser tests run on **Chromium only** (desktop and phone width); Firefox and Safari are untested. The Vite dev-proxy mode (`npm run web:dev`) is a developer convenience that the automated suite doesn't exercise (tests use same-origin serving). | Cross-browser check W7/W8 |
| W-2 | Security | `__Host-` cookie, HSTS and Secure flag are exercised only in configuration and unit paths; not yet tested behind a real TLS proxy. | W8 |
| W-3 | Auth | Account recovery is admin reset only; no self-service email (U2). Login across multiple organizations is intentionally refused (single-org V1). | Business decision / future SaaS |

| W-6 | API | ~~TAS v2.0 §3.4 gaps~~ resolved in W2 (D33–D36). W4 commands declare `idempotency: 'required'` (D39/D40). Remaining: W6 approval/receipt commands when implemented. | W6 |

| W-8 | Storage | If a request fails *after* the object is written (e.g. an idempotent upload's outer transaction rolls back on a 5xx), the object can be left orphaned. The direct failure path deletes it. A periodic orphan sweep is needed. | W7 hardening |

| W-35 | Security | No malware scanner is integrated (U3 still open); every upload is `not_scanned` forever. Only `not_scanned`/`clean` are downloadable, which was already true before W8. | Resolve U3 or formally accept the documented restricted-upload posture (DECISIONS.md D47) |
| W-36 | Storage | `reconcileStorage()` (orphaned-object/missing-file sweep) exists but is not wired into a scheduled job; it must be invoked manually today. | Wire into a cron/scheduled task once a deployment platform is chosen |

| W-39 | Deployment | The Dockerfile/docker-compose stack was validated for syntax only (`docker compose config`); an actual `docker build`/`docker compose up` was not run (Docker daemon unavailable in this session), and nothing was verified behind a real TLS-terminating proxy. | Build and run before relying on it; verify HTTPS/cookie behavior against the real proxy before go-live |
| W-40 | Deployment | U4 (cloud provider), B7 (email delivery), U2 (password recovery), F1 (depreciation), B2 (bulk-tracking policy), and B6 (approved RPO/RTO) all remain open business/infrastructure decisions; see DECISIONS.md D47 for the full classification. | Business-owner decisions required; not an engineering task |
| W-41 | Physical audits | ~~`audits.ts`'s `correctLocation` read and updated `assets.location_id` without first taking a `FOR UPDATE` lock on the asset row~~ **Resolved in W9.2** (DECISIONS.md D50): the read now takes `FOR UPDATE`. Found during the W9.1 architecture review (D48, C1); fixed while wiring the C1 lease-check into the same call site. | Resolved |
| W-42 | Offline (W9) | **Product direction changed to cloud-only (DECISIONS.md D53): the W9.3–W9.6 desktop agent was built and has since been removed.** W9.2's server-side foundations remain (device enrollment/trust/revocation, exclusive leases, asset-code range reservations, online-write protection), as does W9.7's gated sync ingestion. No synchronization protocol, local outbox, or offline command execution is reachable by any client today, since the agent that would have driven them no longer exists. | Resolved by product decision; no further desktop-agent work planned |
| W-43 | Maintenance | `maintenance.ts`'s `closeTicket` mutated `assets.operational_status` without ever taking a row lock on the asset (only the maintenance ticket was locked). Found while wiring W9.2's C1 lease-check into every asset-mutating entry point (DECISIONS.md D50) — the same class of gap as the pre-existing W-41, independent of W9. Fixed in the same change: the asset row is now locked before its status is changed. | Resolved |
| W-45 | Offline (W9, server-side) | Device trust (DECISIONS.md D49/B) is implemented as a human administrator's free-text attestation (`trust_notes`) only — there is no MDM/Intune or other device-management integration anywhere in this codebase to technically verify a device is actually IT-managed, BitLocker-encrypted, or meets the approved baseline. The approved decision wording ("device-management verification must come from the actual IT-managed device baseline, not a client-side claim") is narrower than what's enforceable today; nothing stops an administrator from approving a device based on an inaccurate note. Found during the D51 architecture re-verification. **Still unresolved; unaffected by the D53 desktop-agent removal** — `SYNC_UPLOADS_ENABLED` stays off by default for this reason regardless of what client (if any) would call it. | Build an actual device-posture integration before relying on this in production, or have the business owner explicitly accept attestation-only trust as sufficient (a decision, not yet made) |
| W-44 | Offline (W9.2, server-side) | The offline-lease fencing epoch (`fencing_epoch_seq`) is not yet restore-safe: a `pg_restore` of an old backup restores the sequence to its backed-up value, so a lease epoch issued after the backup could in principle be reissued after a restore (DECISIONS.md D49/G, D50). The safe prerequisite (the real sequence) is implemented and used by every lease; the cross-restore watermark is not, since it needs state outside a routine `pg_dump`. The W9.7 sync-upload path checks `fencingEpoch` against the lease's live row *and* stays behind `SYNC_UPLOADS_ENABLED` (default off) until this is resolved; **unaffected by the D53 desktop-agent removal** — the gate exists for any future caller of these server commands, not only the removed agent. A manual operational step is documented in `docs/BACKUP_RECOVERY.md`. | Resolve before setting `SYNC_UPLOADS_ENABLED=true` anywhere real uploads could occur |
