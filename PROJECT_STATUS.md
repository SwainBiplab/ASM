## W6 (procurement, configurable approvals, purchase orders, goods receipt) — complete
- **Purchase requests:** draft (create/edit/replace line items), submit, approve/reject via the configured policy, cancel (owner on draft/submitted, or `procurement.approve` administratively on submitted); request number `PR-NNNNNN`; totals are integer minor units summed from line items, never floating point.
- **Configurable approval engine (TAS §12.2):** `approval_policies` is versioned — editing creates a new row (`policy_group_id` stable, `version` increments, `is_current` flips) rather than mutating the one an in-flight instance already snapshotted. Each step requires exactly one of a role key or a named user (DB `CHECK`). Policy selection at submission picks the active, current policy for the transaction type with the highest `min_amount_minor` the request's total still clears (NULL threshold = catch-all); no match fails safely with `STATE_CONFLICT`, never auto-approval. At decision time: step order, actor eligibility (role membership or named match), current pending status and self-approval (when `prevent_self_approval`) are all revalidated against the snapshotted policy, not live state.
- **Purchase orders:** created only from an `approved` request; each line must reference an approved request line, and the DB-locked ("lock the request item, re-read, then compare") check prevents ordering beyond what that line authorized, even under concurrent order creation. Amendments (quantity, unit price, delivery date, notes) are tracked in an append-only `purchase_order_amendments` table with a mandatory reason; a line cannot be amended below its already-received quantity. Cancellation is only allowed before any receipt.
- **Goods receipt (separate workflow from approval, TAS §12 explicit requirement):** partial receipts across multiple receipt records; outstanding quantity is `ordered − accepted − damaged` (rejected stays outstanding, pending redelivery or a written-off resolution); the PO-item row lock serializes concurrent receipts against the same line, so two simultaneous over-receipt attempts cannot both succeed (`STATE_CONFLICT` for the one that would exceed outstanding). Discrepancies (damaged/rejected quantities) are flagged `open` and resolved via a dedicated action with required notes.
- **Asset/bulk-stock registration from receipt:** individually tracked lines require one unit entry (serial number, disposition) per received unit; an `accepted` unit creates a ready/new asset, a `damaged` unit creates a non-operational/damaged asset (never available for allocation), a `rejected` unit creates no asset at all. Each created asset carries the supplier, PO number as purchase reference, acquisition cost from the PO line, and chosen location. Quantity-tracked (bulk) lines post one `stock_movements` row and update `bulk_stock_balances`; damaged/rejected bulk quantities never increase the available balance. A `goods_receipt_units(organization_id, asset_id)` partial unique index and a `stock_movements(organization_id, receipt_item_id)` partial unique index back the dispatcher's `Idempotency-Key` replay so a retried receipt can never double-register an asset or a stock movement.
- **New DB objects (migration 0007):** `purchase_requests`/`purchase_request_items`, `approval_policies`/`approval_policy_steps`/`approval_instances`/`approval_decisions` (decisions append-only), `purchase_orders`/`purchase_order_items`/`purchase_order_amendments` (append-only), `goods_receipts`/`goods_receipt_items`/`goods_receipt_units`, `stock_movements` (append-only) and `bulk_stock_balances` — all organization-scoped with composite FKs, matching every prior phase's convention. No new permission keys were needed; the existing `procurement.*`, `receipts.record`, `approvals.configure` and `finance.view_cost` catalog already covered the full action surface.
- **Browser screens:** Purchase requests (list/draft editor/detail/submit/cancel/documents), Approvals (my queue with decide; policy administration with versioned editing), Purchase orders (create from an approved request/list/detail/amend/cancel), Goods receipt (create with per-unit or bulk-quantity entry/list/detail/resolve discrepancy) — all against real PostgreSQL-backed API data, wired into the existing shell/navigation.
- **Known simplifications (documented, not hidden):** purchase-request ownership in the browser's edit/submit/cancel button visibility compares the requester's display name rather than user id (a UI convenience only — the server's authorization check is exact and authoritative); no model picker on request/order line items (category only) to control scope; warranty dates are not set on receipt-created assets (no warranty-duration source exists yet on category/model); no second approval cycle for a PO amendment itself, only an audited reason trail.

## W7 (financial and management reporting) — complete
- **Scope:** five report families per TAS §14/§17, all server-computed against real PostgreSQL records, all enforcing `reports.view`/`reports.export`/`finance.view_cost` on every path (command, CSV export route, and drill-down): asset acquisition and valuation; maintenance expenditure; procurement and receiving summary with traceability; warranty and lifecycle; disposals and proceeds. Plus two new dashboard metric blocks (`procurement`, `finance`), reusing the existing `xMetrics(db, ctx)` null-when-unauthorized pattern.
- **Financial correctness (TAS §14.2):** every monetary total is computed in integer minor units and grouped **by currency** (`CurrencyTotal[]`); nothing is ever summed across currencies anywhere in `reports.ts` — there is no exchange-rate policy to justify it. Cost/proceeds columns are `null` end-to-end (not just hidden in the UI) for a viewer without `finance.view_cost`; the SQL still computes counts and non-financial columns so the rest of the report stays useful. Assets missing `acquisition_cost_minor` or `purchase_date` are flagged `missingFinancialMetadata` rather than silently treated as zero-cost, and the asset valuation report can filter to exactly those rows. Acquisition cost, maintenance expense, purchase commitment (order total), accepted-receipt value, and disposal proceeds are five distinct figures that are never conflated into one "spend" number.
- **Procurement traceability without double-counting:** the procurement report's "received value" sums `unit_price_minor × accepted_quantity` per PO line (not per receipt, not per asset) and "outstanding value" is `ordered − accepted − damaged` priced at the PO's own unit price — so a single PO line contributes exactly once to each bucket regardless of how many partial receipts touched it. A **rejected** quantity is excluded from received value and does **not** reduce outstanding (TAS: "never treat rejected goods as available inventory" — rejected goods are still owed, not fulfilled). Open discrepancies link through to the actual receipt record for drill-down, not just a receipt number string.
- **Depreciation remains explicitly disabled** (`DEPRECIATION_ENABLED = false` in `src/shared/reports.ts`): F1 (depreciation policy) is still unresolved in DECISIONS.md/KNOWN_ISSUES.md, so W7 implements acquisition-cost and operational financial reports only, with no net-book-value figure presented anywhere, authoritative or otherwise.
- **Security corrections made during this phase, not left for a later review:** every report and CSV export route calls `assertPermission` before touching the database (verified by a dedicated no-`reports.view` test getting `PERMISSION_DENIED`/403 at both the RPC and raw-HTTP-route level); CSV cells go through the existing `toCsv` formula-injection guard (verified with a category literally named `=cmd|/c calc`); every report query filters by `organization_id` from the session, never from client input (verified by a cross-organization export test).
- **Browser:** one `ReportsPage` with five tabs (reusing the existing `Tabs` component, matching the Approvals page's precedent for a multi-view module), each with its own filters, currency-grouped totals, paginated table, CSV export button (hidden without `reports.export`), and drill-down links into the existing asset/receipt detail pages. The "Financial reports" and "Reports and exports" nav placeholders are merged into one active "Reports" item.
- **Known limitations (documented, not hidden):** the asset valuation report's "department" column only resolves when the asset is actively assigned to an employee or a department directly — custody held via a workstation, team, or pool has no single resolvable department and shows blank (TAS §17 accepts "best available dimension"); the procurement summary report has no CSV export for its two aggregate tables (request/order totals), only for the itemized open-discrepancy list, since the aggregates are already fully visible on screen; "awaiting inspection"/"under maintenance" lifecycle reporting reuses the existing asset valuation filters (operational status) rather than a dedicated sixth report.
